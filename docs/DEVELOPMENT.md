# Development and Agent Guide

This guide is the repository handoff for human developers and coding agents.
For BlissOS Community ISO invariants, pure-bionic native artifact build commands
(`droidcloud_ril.c`, `droidcloud_bt.c`, `unppu.c`), and zero-downtime controller
rules, also read [AGENTS.md](../AGENTS.md).

## Ground Rules

- Preserve the single-host architecture unless a task explicitly changes it.
- Never add private keys, passwords, session tokens, VM metadata, AVD disks,
  uploaded APKs, or logs to Git.
- Keep ADB, VNC, websockify, and controller listeners on loopback.
- Never restart the live controller service without explicit operator approval
  while user VMs are running (`KillMode=mixed` terminates VMs in its cgroup).
- Be honest about hardware limits: x86_64 KVM VMs have no hardware TEE/KeyMint
  and cannot guarantee Google Play Integrity `MEETS_DEVICE_INTEGRITY` or
  `MEETS_STRONG_INTEGRITY` verdicts.
- Test the normal entry point, including an existing installation where the
  change can affect runtime settings.
- Keep the controller standard-library-only unless a concrete dependency is
  necessary and documented.

## Configuration Rule

Use `controller/settings.py` as the only runtime configuration source. Do not
hardcode:

- `/home/<user>`
- `/opt/droid-cloud`
- public hostnames or IP addresses
- SDK paths
- API or web bind ports
- the operating-system SSH user

When a new setting is necessary:

1. Add it to `settings.py` with a safe local default.
2. Document it in `config/droid-cloud.env.example`.
3. Emit it from `scripts/install.sh`.
4. Update systemd or Caddy templates if another process needs it.
5. Add a focused test.

## Lifecycle Invariants

- Metadata is written atomically.
- A start is complete only after ADB boot completion.
- Stop and restart operations use a per-machine operation lock.
- Cloning is allowed only while the source is stopped.
- Hardware edits are allowed only while stopped.
- Process groups are terminated as a unit.
- VNC tokens are regenerated by the controller and never committed.
- Port allocation checks metadata and live listeners.

## API and Frontend

The frontend uses same-origin cookies. Mutating requests must preserve the
origin check. When the API shape changes:

1. Update `server.py`.
2. Update `web/app.js`.
3. Add a template-level test if parsing or validation changed.
4. Update `docs/ARCHITECTURE.md`.

There is no bundler. `node --check web/app.js` is the syntax gate.

## Deployment Changes

Templates use `@KEY@` placeholders. Keep them renderable by
`scripts/render-template.py`. Service units must reference environment-derived
paths wherever systemd variable expansion is supported.

Run:

```bash
./scripts/check.sh
```

Before a deployment change, also render the templates to a temporary directory
and inspect the output.

## Test Strategy

Unit tests cover configuration mapping and pure validation. End-to-end Emulator
tests require KVM and are not part of the default suite.

For a staging deployment:

1. Use a separate install directory.
2. Use a separate state, cache, SDK, and AVD root.
3. Use a separate hostname.
4. Stop the instance before changing service configuration.
5. Create one VM, verify boot, dashboard input, ADB tunnel, and shutdown.
6. Check that only Caddy is publicly bound.

## Code Review Checklist

- Does the change work through the dashboard and API normal path?
- Are existing AVDs and metadata still readable?
- Are failures safely retried or surfaced without corrupting state?
- Are secret and runtime files still ignored by Git?
- Are all paths configurable?
- Are public and loopback listeners unchanged or intentionally documented?
- Are docs and checks updated?
- Does `./scripts/check.sh` pass?
